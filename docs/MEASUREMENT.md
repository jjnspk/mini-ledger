# 측정 조건

전략만 바꾸고 나머지는 전부 고정한다.
이 문서의 조건이 바뀌면 이전에 측정한 숫자는 모두 무효이며, 전 전략을 다시 측정한다.

## 1. 측정 지점

HTTP가 아니라 **서비스 레이어를 직접 호출**해서 측정한다.

HTTP로 재면 톰캣 스레드 풀과 커넥션 풀의 포화가 락 대기 시간과 뒤섞여서,
락 전략 사이의 차이가 묻힌다. 이 실험의 관심사는 API 성능이 아니라
동시성 제어 방식의 비용이므로 측정 지점을 아래로 내린다.

측정 대상: `AccountService.withdraw(accountId, amount)` 호출 시작 ~ 반환/예외

## 2. 지표 정의

| 지표 | 정의 |
|---|---|
| 처리량 | 완료 요청 수 ÷ (마지막 요청 종료 시각 − 첫 요청 시작 시각), ops/sec |
| p95 지연 | 전체 요청의 지연 시간을 정렬했을 때 95번째 백분위 (ms) |
| 재시도율 | 전체 재시도 횟수 ÷ 총 요청 수. 한 요청이 3번 재시도하면 3으로 센다 |
| 실패율 | 기술적 실패 건수 ÷ 총 요청 수 |
| 데드락 | 측정 구간 동안 발생한 데드락 건수 (MySQL 로그 기준) |

### 실패와 거부를 분리한다

- **정상 거부**: 잔액 부족으로 출금이 거절됨 → 실패가 **아니다**. 올바른 동작이다.
- **기술적 실패**: 락 대기 타임아웃, 데드락으로 인한 롤백, 낙관적 락 재시도 횟수 소진
  → 이것만 실패율에 넣는다.

둘을 합쳐서 세면 "잔액이 바닥나서 거절된 것"과 "락 때문에 처리하지 못한 것"이
구분되지 않아 전략 비교가 불가능해진다.

## 3. 고정 조건

| 항목 | 값 |
|---|---|
| 동시 스레드 수 |  32 |
| 총 요청 수 |  1,000 |
| 요청당 금액 | 1,000원 고정 (랜덤 금액은 쓰지 않음) |
| 워밍업 |  100건 실행 후 DB 상태 초기화, 이후 본 측정 |
| 반복 |  5회 실행, 5회 값을 모두 기록하고 중앙값을 표에 쓴다 |
| 커넥션 풀 | HikariCP maximum-pool-size = 20 |
| 격리수준 | REPEATABLE READ (InnoDB 기본값) |
| 락 대기 타임아웃 | innodb_lock_wait_timeout = 5초 |

중앙값만 쓰고 5회 값을 버리지 않는 이유: 회차 간 편차가 크면
그 자체가 관찰 대상이다 (예: 낙관적 락은 편차가 클 것으로 예상).

## 4. 시나리오

### A. 정합성 시나리오 : 불변식이 깨지는지 확인하기
- 계좌 1개, 초기 잔액  500,000원 (= 총 요청의 절반만 감당 가능)
- 32 스레드 × 1,000건 출금
- 검증: 최종 잔액이 0 이상인가 / 성공 건수 × 1,000원 = 초기 잔액 − 최종 잔액인가
- 성능 지표는 참고용으로만 본다

### B. 성능 시나리오 : 락의 순수 비용 확인
- 계좌 1개, 초기 잔액  10,000,000원 (모든 요청이 성공 가능)
- 32 스레드 × 1,000건 출금
- 잔액 부족 거부가 섞이지 않으므로 처리량/지연이 락 비용만 반영한다
- **측정표의 숫자는 이 시나리오에서 나온 것이다**

### C. 분산 시나리오 : 경합이 줄면 어떻게 달라지는지 본다
- 계좌  10개, 각 초기 잔액 1,000,000원, 요청을 균등 분배
- B와 비교해 경합 수준이 처리량에 미치는 영향을 본다

## 5. 실행 환경

| 항목 | 값 |
|---|---|
| 기기 |  MacBook (Apple Silicon), Docker Desktop |
| MySQL | 8.4, Docker Compose로 기동 |
| JVM | Java 21 |

**절대값은 의미가 없다.** Docker Desktop의 가상화 계층 때문에 같은 코드도
다른 기기에서 다른 숫자가 나온다. 이 측정표는 동일 기기·동일 조건에서의
**전략 간 상대 비교**로만 읽어야 한다.

## 6. 한 번의 실행 절차

1. DB를 초기 상태로 되돌린다 (계좌 삭제 후 재생성)
2. 워밍업 100건 실행
3. DB를 다시 초기 상태로 되돌린다
4. 스레드 풀 32개로 1,000건 주입, 요청별 지연·결과·재시도 횟수를 기록
5. 전체 종료 후 집계, 최종 잔액 검증
6. `docker compose logs mysql | grep -c "TRANSACTION.*DEADLOCK"` 으로 데드락 수 확인

## 7. 측정하지 않는 것

- 네트워크 지연 (서비스 레이어 직접 호출이므로 HTTP 계층 없음)
- 다중 노드 / 분산 트랜잭션 (단일 DB 전제)
- 장시간 부하에서의 안정성 (1,000건 단발 실행만 본다)
